# 持久化逐消息批量判定

## 目标与结构

新算法代替生产原先的单快照正文/`<noreply>` 决策。并非一条消息一次收费请求；同一调用可处理多条有稳定 ID 的待判输入。

- `batch_protocol.py`：完整 schema、整数 ID、布尔值、原顺序、每项正文与完整 ID 覆盖验证。
- `batch_store.py`：SQLite WAL + synchronous=FULL，事务性输入、整批判定、去重和发送 ledger；不用 AstrBot 核心数据库。
- `batch_runner.py`：单调度器、每群单 worker、公平并发上限、自动到期唤醒、每项退避和独立发送。
- `batch_transport.py`：不持有旧 event、SDK 客户端或凭据的持久化路由；恢复后找到当前平台实例发送。
- `main.py`：来源 AI、人设、scope、身份、生命周期和原版上下文 gate。

## 模型协议

以下 ID 和正文仅是协议示例，不是实际运行结果：

```json
{"decisions":[{"id":101,"reply":false},{"id":102,"reply":true,"text":"需要发送的正文"}]}
```

输入是 `{"background":[...],"pending":[...]}`；观察均为不可信聊天内容，而非系统指令。仅 pending 要判断，background 不生成额外任务；可以参考后文发现前文已被回答或撤回。每项带稳定整数 ID、发送者和 nullable 身份标记。

先完整验证整批，再事务提交；不部分提交，不将缺漏自动补成 false。提示词要求裸 JSON；兼容剥离一层完整的 json/JSON/无语言标记代码围栏后再做相同的严格校验，不搜索 JSON 子串、不修补缺失内容。拒绝围栏外说明、多段围栏、截断、独立 `<noreply>`、重复 JSON key、乱序/重复/未知 ID、非布尔 reply、空/过长/控制标记正文、非 assistant role 与意外 tool calls。只把每项正文交给平台，绝不外发内部判断数组。

默认最多 32 条待判/次。失败后缩小重试批次，失败项有独立持久化 retry_after/attempts；后续健康项可先完成判定，不让一条持续非法消息独占全群。每批仍按 ID 顺序验证。发送保持原消息顺序，不能越过更早未判或不确定发送项。

## 持久化与覆盖

数据路径：插件数据根下 `batch/queue.sqlite3`，不在插件源码或框架历史库里。目录 0700、DB 0600，WAL/SHM 留在私有目录。

每条合格输入先提交到数据库，随后才能唤醒模型 worker；平台重复 message_id 在同群去重。没有平台 ID 时使用内部新 ID，不假称能识别平台重投。每条输入状态：`pending` / `judged` / `cancelled`。`reply=false` 是有效判定，busy/cooldown/异常不是。

背景最多 300 条，用户/本地 assistant 共用；当前批 pending 从 background 中去重。未判输入永不因 300 条淘汰被删除，较老 backlog 可以与最近背景共同进入请求，所以 300 不限制 pending。默认字符 caps 均为 0；正 cap 先削减背景，再缩小待判批次。单条仍超限或模型拒绝时，保留 pending 并记录安全错误类别，不虚报成功。

判定尝试间隔支持 0，表示无正常判定节流，并非无限并发或取消错误重试退避；当前正式实例为 0 秒判定间隔、1 秒发言间隔，未修改出厂默认。后台完成、尝试间隔到期、重试到期或发言冷却到期都会自动推进，不需等下一条来信。初始化恢复 ledger，卸载取消内存任务并关闭 DB；中断生成保留 pending。明确清空把待判改为 cancelled；此数不混入 judged。

形式上的进度恒等式是 `received = pending + judged + cancelled`。仅用于进入本支路并成功事务提交的合格输入，不涵盖平台未投递、服务停机时未收到、私聊/正常唤醒/命令/非纯文本、自身明确回声。首次升级不能追补旧算法已丢失的内存窗口。

## 判定与发送分账

合法批次判定提交后，发送状态另为 `none/pending/shadow/cancelled/sending/accepted/unknown`。

1. 每次发送前先事务性 claim 为 sending。
2. QQ 官方调用当前适配器客户端 `post_group_message`，保存返回消息 ID；没有 ID 不确认。
3. 已确认结果不重新判定或重发；确认后添加本地 assistant 背景，bot=true/admin=null，并开始该群配置的发言冷却（出厂 30 秒，当前正式实例为 1 秒）。
4. 明确未发起网络操作（平台尚未就绪等）可安全延后重试，不重新调用模型。
5. 超时、模糊 API 异常、发送中取消/崩溃都记 unknown。重启的 sending 一律转 unknown；不会为追求“完成”而自动重发。
6. unknown 阻塞该群后续顺序发送，但不阻塞其他群，也不阻止继续判定新输入。管理员核实后可用 `/noreply_clear` 放弃未确认旧发言、清掉旧待判并恢复新工作；这不是补认送达。

QQ 在被动锚点被明确拒绝时才尝试无锚点的主动发送，仍受平台权限/配额限制；超时/服务器不确定错误不做这种重放。固定序号只辅助去重，不声称端到端 exactly-once。通用 Context.send_message 的 bool 仅证明匹配平台并派发，收据单独标为 `session:handed_off`。

模型失败可能持续、平台可能一直拒绝、磁盘可能不可写，任何算法都不能保证这些情况下有限时间内完成。写盘失败明确记 ingest_failed 且不称已接收；已有 pending 保留，DB 写错误有退避，避免忙循环。账本元数据不自动删除；需监控磁盘和备份，不能为了容量删未判输入冒充覆盖。

## 常规链路与安全

范围、全局 AI、全群/精确白名单、私聊/显式唤醒/命令分流均保留。QQ 用适配器实例 + qq_official + group ID 统一 @/未 @ 的 self_id 差异。其他 bot 的标记不是过滤策略；只过滤可确认自身的消息/`is_you=true` 回声，避免自激。

原版群上下文 gate 仍为可撤销实例级机制，标准历史与配置不重写。普通纯文本发送通过 after-sent 作为背景观察（非送达证明）；异步自主发送走独立 transport，不假称执行完整 Agent/发送 hook 或打通标准历史。更换配置和显式唤醒使旧发言 generation 失效，旧 pending 仍可被判断，但旧回复不迟到外发。

完整诊断默认关闭。必需的 queue DB 仍含近期输入和回复，只有诊断 JSONL 才是 opt-in 的完整请求/原始模型响应日志。运行日志只记本地 ID、群键哈希、安全类别和状态；invalid_output 额外记录允许列表内的响应形态、JSON 语法错误种类、长度与位置，不含响应片段。fence_accepted 表示外层围栏兼容后已通过整批验证并提交，不是平台送达证明，禁止把队列、运行配置和私有日志放进 Git。

## 实际验证

Mac 的真实 AstrBot 4.29.3 SDK 全套测试通过；Pi 亦使用正在运行实例的实际 4.29.3 SDK / Python 3.12.13，在独立临时 ASTRBOT_ROOT、禁止网络的环境执行完整测试。包括真实 QQ 解析器 → 事件 → JSON 请求 → 判定提交 → 假 QQ API 收据的端到端路径；没有为测试调用收费模型或向真实群发消息。

覆盖完整 ID 校验、忙时补判、定时恢复、持久化重启、300 条实际请求正文与身份、群并发容量、公平调度、永久坏项隔离、发送顺序/冷却、未知发送不重放、显式清空解阻、磁盘错误与自身回声。当前遗留一条 SDK audioop DeprecationWarning，不是功能失败。真实供应商的 JSON 遵循率、回复质量与终端送达仍需运行样本验证，不能拿合成测试冒充真实对话。
