# 群聊上下文设计

## 当前：持久化逐消息批量判定

生产升级主路径为 batch_mode=true，输入按 background/pending 分离；最近背景 300 条，未判消息持久化并独立保留。模型对每个稳定 ID 返回显式 JSON 判断，完整校验后事务提交；发送单独记账，忙时/冷却自动推进，重启恢复。QQ 物理群键统一 @/未 @ 的 self_id 差异；原版上下文 gate 保留，正常 Agent 历史桥接仍未实现。详见 [完整设计](BATCH_JUDGMENTS.md)。

## 旧单快照方案留档

下文保留初期实现对照；涉及整体正文/<noreply>、仅内存窗口、没有 pending 的描述仅适用于 batch_mode=false 的兼容路径，不代表当前主路径。


这不是“复用原版注入格式，仅替换概率判断”。M1 使用独立的观察窗口和直接生成支路；原版群上下文仍服务原有 Agent 对话，两者未在 M3 前统一。

## 当前插件

`Engine.observe()` 记录合格纯文本，以平台实例/机器人/物理群分组，保留角色、发送者 ID、显示名、时间、消息 ID、截断正文，以及 `is_bot` / `is_admin` 身份标记。消息 ID 做摘要去重；超长身份有界。读快照不消费，只有滑窗淘汰、清空或生命周期变化等才移除观察。

当前触发消息先观察，再取窗口快照，因此它包含在 JSON 中一次。`serialize_snapshot()` 把记录编码成 JSON 数组。模型请求采用：

```python
response = await context.llm_generate(
    chat_provider_id=provider_id,
    system_prompt=persona.system_prompt + "\n\n" + PROTOCOL,
    prompt=serialize_snapshot(snapshot),
    contexts=[],
    tools=None,
    request_max_retries=0,
)
```

因此 contexts=[] 不表示没有背景；背景放在本次 user prompt 中，不是从 AstrBot 标准会话历史自动读入。JSON 中的 role 是记录字段，不是把每个观察还原成 API 的独立 assistant/user 消息。

PROTOCOL 要求模型参考人设，选择正文或独立 <noreply>，并把 JSON 当不可信观察而非指令。这是提示与输入边界，不是对提示注入的绝对防护。

插件能观察正常发送阶段的合格纯文本结果，并在 live 时记录本地接受的自主正文；shadow 候选和沉默标记不写成机器人已发言。两种观察都不是平台送达回执。普通未 @ 的非 Plain 混合输入仍跳过；接管的 @ 可提取引用文字，对未提供给模型的媒体保留占位，仍不是识图或多模态摘要。

## 发送者身份标记

每条进入窗口的记录都有两个可空布尔字段：

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| `is_bot` | 平台是否将发送者标记为机器人账号 | QQ 官方原始消息的 `author.bot`；兼容对象属性与原始 payload |
| `is_admin` | 发送者是否具有本事件的 AstrBot 机器人管理员身份 | `event.is_admin()`，不是 QQ 群管理员或群主身份 |

缺失或非布尔元数据编码为 `null`，不将字符串 `"false"` 或整数 `1` 强转为布尔值。平台标记为非机器人账号不保证正文由真人手写；未被平台识别的自动化普通账号仍可能是 bot。

本机器人本地回复固定标记 `is_bot=true`，`is_admin=null`，不会继承触发者的管理员权限。其他机器人的消息仍是外部 `role="user"` 观察，不改成自己的 `assistant` 历史。诊断开启时，incoming 和对应 request 快照都保留这两个字段；旧试验原件不回填。

这些字段只提供身份信息，不改变触发、冷却、权限或发送规则，也没有自动屏蔽其他 bot 的消息。PROTOCOL 说明 admin 的含义及 null 的未知语义。

## 原版屏蔽与恢复

插件接管的群通过运行期实例级 guard 屏蔽内置 `group_context_enabled(event)` 入口，因此原版 `on_message` 不再累计这份缓存，原版请求钩子也不会注入该额外群背景。仅在插件实际启用、来源 AI 开启且处于插件范围时生效；私聊和未接管群保留原行为。原版 UI/文件中的开关和值不被改写，停用插件即按当前原设置恢复，卸载会撤销 guard；内置组件重新加载时会重新绑定。

这不清空正常 Agent 会话历史，也不关闭独立的群消息数据库记录。实际接管的 `@机器人` 已进入插件队列，直接使用同群 300 条窗口并强制回复，不再走默认 Agent；原生 Agent 会话数据库仍未与插件双向桥接。下面是未被 guard 屏蔽时的原版实现说明。

## 原版（本次安装的 AstrBot 4.29.3）

`GroupChatContext.handle_message()` 把消息格式化为带昵称、时间及内容占位/摘要的文本，按 UMO 缓存。`on_req_llm()` 在原版 LLM 请求钩子中，将当前消息之前的缓存拼成 <system_reminder> 背景块，追加到 `req.extra_user_content_parts`，而不是另开一次判断模型调用。

该方法在请求阶段就取走此前缓存及当前记录，保留当前记录之后新到的内容；不是等平台成功回复后才消费。正常会话历史仍由原版 Agent 管理。多模态覆盖较广，支持图片占位/可选描述、分享卡片、@提示与引用摘要；不等于这些内容全部原样作为多模态发给模型。

## 关键差异

| 项目 | 当前插件 | 原版群聊上下文感知 |
| --- | --- | --- |
| 输入位置 | 本次 user prompt 的 JSON 观察快照 | 原版 ProviderRequest 的 extra_user_content_parts |
| 分组 | 平台实例/机器人/物理群 | 原始或隔离后的 UMO |
| 读取窗口 | 非消费式，沉默后保留 | LLM 请求阶段消费此前缓存和当前记录 |
| 本次消息 | 包含在快照一次 | 主 prompt 保留，额外背景排除当前记录 |
| 消息覆盖 | 纯文本，含可观察的机器人纯文本 | 较丰富的格式化内容与占位/摘要 |
| 正常会话历史 | 不自动加载、没有双向统一 | 保留原版会话/Agent 流程 |
| 原版 Agent 能力 | 自主支路不运行 tools、知识库与标准 LLM 钩子 | 按原配置运行 |

当前窗口与出厂默认都调整为最多 **300 条**，`window_messages` 可配置；用户观察与本机器人的本地回复共用窗口，超过条数时从最旧记录开始淘汰。`message_chars=0`、`context_chars=0` 表示不再施加插件额外的正文和完整 JSON 字符截断，取消此前短时试验的 500 / 6000 字符限制。因此实际请求能够包含最近 300 条完整合格观察，而不只是把条数标签改大。

如需主动限制输入成本，仍可将 `message_chars` 设为正整数、`context_chars` 设为至少 512 的正整数。启用总字符限制时，身份元数据与 JSON 转义均计入预算，可能导致实际条数少于 `window_messages`；这些是字符而非 token，系统人设与协议在该 JSON 预算之外。模型服务自身的输入上限仍适用，插件不会偷偷再截成小窗口。

没有按分钟或消息时间戳自动过期的 TTL。沉默、读取快照均不消费窗口；数量/长度淘汰、`/noreply_clear`、插件卸载或进程重启会移除相应观察。窗口仅驻留内存，不是持久会话库，不自动回填数据库历史。

M3 才讨论正常会话与自主插话的临时上下文桥接及人设覆盖优先级。本次身份标记与 300 条窗口调整不改变触发方式、发言冷却或补判行为。
